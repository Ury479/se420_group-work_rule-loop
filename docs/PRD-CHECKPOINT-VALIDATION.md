# RuleLoop：约定节点驱动的验证机制

版本：v0.2 · 2026-09-28  
状态：核心方向经本次对话确认；实现细节为待验证方案；尚未开发或完成使用验收。  
配套交付：[v0 下一步优化提示词](V0-CHECKPOINT-VALIDATION-PROMPT.md)

## 1. 产品结论

**记住当初的期待，在约定节点启动分析，对照实际结果与未知信息，推动一次最小可行性验证。**

唯一核心工作单元是“四段验证卡”。重要支出是第一条验证场景；卡片的表达可以通用，但首轮不扩展成任务、习惯、项目、财务等多个管理系统。

流程：

> 计划：留下期待并约定节点 → 行动：继续原本的学习或工作 → 记录：保留或关联关键依据 → 复盘：到节点对照结果 → 决定：执行一个最小验证 → 下次节点。

产品的价值不以打开频率、卡片数量或分析篇幅衡量，而以是否减少启动与整理负担、补充有用依据、推动具体下一步衡量。低频不自动等于无用，一次有帮助也不足以证明持续价值。

## 2. 事实、确认与假设

### 用户报告的事实

- 小工具累计使用不到三次，但开发已投入约一到两个月；实用性尚待验证。
- 一次重要消费比较中，用户考虑不同用途，意识到现有 Cursor 额度尚够用，约一周后购买 GPT。
- 购买后用户报告：设计模式、动态规划学习有明显推进，浏览器插件中频繁提问；产品工作少量推进，泰拳项目经过考虑暂缓。
- 这些是用户自述，不是本产品自动采集或独立核验的结果。使用次数不等于学习效果，也不能由此推断因果关系。
- 当时提到的金额、币种和套餐口径未完整核实，不用于生成精确收益或价格结论。

### 已确认需求

1. 通过数据对比重新判断当下需要什么，关注已有资源与主线结果。
2. 保留当初期待、已验证结果、未知信息，并决定下一步最小验证。
3. 平时不要求额外日记或重复维护；偏好阶段性回顾，以及利用已有材料后由本人确认。
4. 采用“约定节点”启动，不以固定周报或自动判断停滞作为首版主触发机制。
5. 先验证工具能否解决自己的问题，再决定是否继续开发。

### 待验证的实现假设

- 首轮只聚焦一个当前主线、一张真实卡；允许保留其他历史，不同时扩张多个活动流程。
- 通过明确日期或手动确认里程碑触发；里程碑另约一个兜底检查日期。
- 应用外提醒可能是必要条件，具体渠道尚未选定。
- 关联现有笔记和集中粘贴材料，可能比另建记录系统更合适；自动读取 Obsidian、浏览器或 AI 历史尚未获选，也尚未实现。
- AI 可辅助整理候选证据，但不能替用户确认结果；Jev 不是本轮验证前提。

## 3. 四段验证卡

| 固定栏目 | 内容要求 | 防止的误判 |
|---|---|---|
| 当初的期待 | 一句话主线、希望发生的具体变化、当时背景；支出场景可关联已有资源和换算快照 | 不以今天的目标覆盖过去的期待 |
| 你验证的结果 | 实际发生的事情、来源、日期、确认状态；区分用户自述、可查看材料和待确认候选 | 不把提问频率、AI 总结或空记录直接当成有效结果 |
| 未知的信息 | 当前缺什么依据；哪些期待尚不能判断；必要时写待核实问题 | 缺少记录不等于没有进展；不编造数据 |
| 这次的决定：先进行最小可行性验证 | 一个动作、要回答的问题、观察标准、约定节点 | 不用“继续努力”“再研究”充当下一步 |

“间隙”暂定义为：期待与实际结果之间的差距，以及解释差距时缺少的证据。先展示可追溯事实，不生成综合价值分、虚构 ROI 或“正确消费”结论。

量化仅在口径明确时使用。例如可记录金额与币种、统计周期、可核实的任务完成次数；不能把不同币种直接相加，也不能将未使用额度或放弃消费自动算作实际收益。首轮允许只有定性证据。

## 4. 首轮用户流程

### 4.1 留下期待

- 从消费换算结果进入“约一次验证”，也允许直接创建卡片。
- 最少填写：当前主线、期待变化、回访节点。金额、资源状态、来源链接均可选。
- 复用已有输入，不要求重新填写长表单；购买、暂缓、放弃都可进入验证，不把购买当作成功。
- 第四栏在首次创建时可以为空；结果与未知区域显示“待回访”，不能预填成功证据。
- 支出入口保留价格/汇率快照语义，卡片不依赖换算器才成立。

### 4.2 等待节点

- 日期型：用户选择日期、时间和时区，支持修改或取消。
- 里程碑型：例如“完成一次作业后”，由用户确认完成；另设兜底检查日期。首轮不声称能自动判断外部任务完成。
- 等待期间不要求签到或每天写记录。可随手添加来源，但不是完成回访的前提。

### 4.3 启动分析

- 到节点后，展示“当初期待＋已有材料＋尚待确认的问题”，直接进入卡片。
- 应用内队列只解决打开后的定位，不算已实现应用关闭时的主动提醒。
- **实用性验证必须包含一次应用外启动路径。** 首轮建议采用用户已有日历的一次性提醒，附中性标题和可访问的卡片链接；也可先人工提醒完成验证。此处是实验方案，不表示已创建提醒。
- 日历方案必须实际确认添加成功；单纯生成下载文件不算提醒已送达。链接需在用户实际设备上可打开，本地开发地址不可假定手机可访问。
- 正式通知通道待首轮实验后选择，不在本轮引入后台调度、推送基础设施或系统权限申请。
- 可立即回访、改约具体节点、暂停或结束。错过提醒不自动判定失败，不产生堆积催促。
- 修改/取消节点时同时提示处理外部日历旧提醒；未实现同步时不得宣称自动撤回。

### 4.4 对照结果与未知

- 用户可粘贴近期材料摘要、添加来源链接，或直接口述/填写简短结果。
- 没有材料时允许“暂不知道”，并转向一个补证据的小动作。
- AI 如被启用，只提出候选整理；展示依据，由用户确认或纠正后归入“你验证的结果”。无 AI 也能完成全部流程。
- 不要求连接全量私人记录；不自动上传笔记、消费类别、聊天或附件。
- 对照当初主线，区分“做了很多”“完成了具体事”“获得了用户认可的帮助”。

### 4.5 决定并启动下一轮

- 选择一个最小验证：写明问题、动作、观察标准和下一节点。
- 保存为新一轮，不覆盖上一轮期待和结论。主线变化时写出变化时间与理由。
- 用户也可明确暂停或结束，不强迫无限验证；结束需保留简短理由。

## 5. 首版边界与旧功能归属

| 既有内容 | 本轮处理 |
|---|---|
| 消费换算 | 保留为已有使用价值的入口，关联到验证卡；不扩展价格目录或套餐导购 |
| 冷静期 | 作为购买前等待/再次考虑的可选阶段，与购买后的验证节点区分 |
| 记录、复盘、档案 | 收敛为同一卡片中的依据、对照和历史；不要求多次录入 |
| 规则库、通用行动助手 | 暂不作为开发主线；不删除已有数据或路由 |
| Jev / 其他模型 | 延后，直到某个明确判断任务的收益能够被验证 |
| 全量 Obsidian/聊天导入、自动进展识别 | 延后；先验证少量材料集中补充能否接受 |
| 签到、经验值、排行榜、复杂图表、财务收益评分 | 不纳入首版 |

通用性体现在卡片结构，不体现为新增多个业务模块。与 AI 聊天的区别是持续保存背景、在节点启动、提供可追溯依据；不声称 AI 绝对无法完成这些工作。

## 6. 最小信息与状态

这是概念契约，不是已经落库的数据库方案。

- 验证主题：id、标题、创建时间、当前主线。
- 验证轮次：期待快照、当时背景、可选支出/换算关联、主线变化说明。
- 节点：日期/里程碑、到期时间、时区、兜底日期、提醒渠道与配置状态。
- 证据：内容、来源引用、发生/导入时间、用户自述/材料/AI候选类型、用户确认状态。
- 未知：问题与相关期待；允许“还不确定”保留至下一轮。
- 决定：待验证问题、单一动作、观察标准、下一节点，或暂停/结束理由。
- 状态：草稿 → 等待节点 → 待回访 → 回访中 → 本轮完成；可暂停/结束。

节点到期不是回访完成，提醒发送不是用户已读，用户已读不是行动完成。日期跨时区按实际时间比较；界面明确显示用户选择的时区。同一轮到期只能出现一个待回访项。改约更新节点并保留历史。

正式个人试用需要真实持久化、草稿恢复和数据导出；跨设备、应用外提醒依赖另行验证。演示原型必须标明示例数据和模拟提醒，不将内存状态包装成已保存记录。

## 7. 信息架构与设计要求

### 7.1 页面表达补充（2026-09-28，设计提案）

四段结构不是四个同权空表单。首页应先呈现“当前要判断的问题”，详情通过期待与相关证据对照揭示未知，再允许从某条未知直接创建一个最小验证。产品减少的是重新组织背景与启动分析的负担，而非仅增加记录字段。

主案例采用工具自身的实用性判断：

- 当前问题：这个工具值得继续开发吗？
- 当初期待：帮我更有依据地安排重要支出，服务长期计划。
- 用户报告的结果：总共使用不到三次；消费换算帮助过一次 GPT 购买决策；开发投入约一到两个月。
- 未知：能否持续提供帮助；节点回访是否比 AI＋Obsidian 更省事。
- 最小验证：先完成一次真实回访，观察是否补出遗漏信息并形成一个具体下一步，再决定是否继续开发。

该案例用于带标识的设计演示，不作为已落库的个人记录；日期未约定、持续效果未证实。GPT 消费作为次级演示，检验通用表达。具体页面映射、交互文案和验收路径见配套 v0 提示词 v0.2。

下一轮任务应修改实际页面对应的设计和交互：检查真实路由，复用现有组件；未完成视觉验收时交付隔离页面预览，验收后接入对应生产页面。不能仅生成脱离现有产品的独立展示站。下述三个核心界面是核心任务分组，不是强制删除旧页面或锁死总页面数；消费入口与历史页也需按其职责衔接。

### 7.2 核心任务与视觉基线

首轮只设计三个核心界面，不锁定生产路由：

1. 当前主线：一个当前目标、当前验证卡、约定节点；到期时只有一个主行动“开始这次验证”。
2. 创建/约定：简短期待与节点设置，可附已有资源或支出。
3. 验证详情：固定四段结构、证据来源、确认/纠正、最小行动、改约/暂停/结束；历史为次级展开。

先遵守 AGENTS.md 的设计优先流程，阅读 guizang-ppt-skill，形成可评审高保真原型并进行浏览器/截图评审，再进入生产实现。此次仅形成需求和提示词，未执行视觉或生产开发。

现有 document-grounded-dark-game 设计说明记录了深色偏好。下一轮可以继承其色彩与排版基线，减少装饰；四段证据比游戏属性、数字墙更优先。保留移动端可用性、可见焦点、语义标签、非颜色状态提示与减少动效支持。外部资源不得使用 latest，能本地化时优先本地化。

## 8. 可检验的验收场景

- AC-01：填写主线、期待、有效日期/时区后可约定验证；没有购买也可创建。
- AC-02：未到节点显示等待；到期只出现一个回访项；重开后保留卡片与草稿（生产阶段）。
- AC-03：里程碑未确认时，不伪造完成；兜底日期到达可启动检查。
- AC-04：仅应用内显示待办时，明确不能证明应用外提醒可用；试用需记录外部提醒是否实际到达、是否打开。
- AC-05：无材料可以如实记录未知，仍能制定补充依据的最小动作。
- AC-06：AI候选未经确认不得展示为已验证结果；来源无法访问时保留缺失提示。
- AC-07：保存下一步验证需有具体动作、观察标准和节点；暂停/结束可替代下一轮。
- AC-08：第二轮不覆盖第一轮；目标变化有记录，不静默重写过去期待。
- AC-09：改约、取消或暂停后应用内状态一致，并说明外部提醒是否需要手动更新。
- AC-10：金额/单位缺失时不推算精确价值；不把使用频率或消费放弃金额当作收益。
- AC-11：原型明确区分示例、模拟和真实能力；旧路由/记录不被未授权删除。
- AC-12：无需每日记录、无需启用 AI、无需连接全量私人材料，也能走完一次回访。

## 9. 第一轮实用性实验：先不扩大开发

对象：一笔真实重要支出，例如 GPT；具体回访日期由用户后续选择，本文件不创建任何自动化。

方法：用最小原型或手工卡保存期待，约定一次可到达的外部提醒；到节点集中整理少量现有材料，用户确认四段内容，执行一个最小验证。

记录以下实验事实：

| 观察 | 判断用途 |
|---|---|
| 提醒是否到达、用户是否因此启动 | 判断是否解决忘记回访，而非增加静态页面 |
| 准备材料和完成回访分别花多久 | 判断是否比既有 AI＋Obsidian 流程更省事；无基线时先记录，不伪造节省比例 |
| 是否补出一条原本遗漏/不清楚的依据 | 判断数据整理是否带来帮助 |
| 是否形成具体动作，以及到下一节点是否执行 | 判断分析是否进入行动；决定不变也可能有价值，但要说明减少了什么不确定性 |
| 用户是否愿意为下一笔重要投入继续使用 | 作为继续验证的信号，不当作已证实长期留存 |

建议继续条件：回访能实际启动、补出有用依据或减少整理负担，并产生可执行下一步。建议停止或缩减条件：用户本来已清楚结论、需要重复搬运大量材料、回访仍全靠本人想起，或连续实验只是增加分析却没有帮助。单次通过只支持下一轮，不支持全面产品化。

首轮过后再决定三个候选优化：已有资源对比、证据收集辅助、提醒渠道可靠性。优先解决实测阻力，不先接模型或扩页面。

## 10. 文档优先级与迁移

本文件是本次优化的产品方向依据。旧 FEATURE v0.2、旧 ROADMAP 和消费换算 PRD 保留为历史范围/技术参考，不能据其默认要求先做完整八页、规则库、规则准入或成长指标。新验证卡不要求“重复错误或高影响”门槛。

旧架构的本地优先、隐私与数据保护约束继续作为参考，但现有源码仍是原型，不因新 PRD 而视为已完成。生产数据迁移、提醒渠道、证据导入方式与持久化实现待实用性及设计验证后确定；不删旧数据、不静默迁移。
