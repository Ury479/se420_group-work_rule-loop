# 先装修再开业：独立产品官网优先上线方案

版本：v0.1 · 2026-09-28  
状态：流程设计稿；尚未实施网站开发、部署、GSC/GA4 配置或收录验证。  
适用：面向公开用户、需要验证需求的独立产品；附 RuleLoop 适配说明。  
GEO：Generative Engine Optimization，指提高内容在生成式搜索中的可发现性与可引用性。

## 1. 固定执行顺序

**产品 UI 概念与高保真基线、API v0 契约完成 → 官网设计验收 → 优先上线 Landing Page、Pricing、Waiting List 与 GSC/GA4 → 上线后开展 SEO/GEO 优化 → 根据真实意向交付最小产品。**

这里的“API 完成”是首版范围内接口文档可评审、可联调，不要求完整后端先做好。官网必须有真实留资能力，其余产品能力按验证结果推进。

基础 SEO 随首次部署交付；内容扩展、搜索表现与生成式搜索表现的优化放在部署后。不能上线一张不可抓取的空壳，再把修复基础可访问性算成增长优化。

引用材料中的“两小时收录”“四天完成”“上线即出单”是个案，不能直接设为项目验收指标。一周作为第一轮观察节点；索引建立、找到合适受众和验证付费需求是不同问题。

## 2. 阶段、交付物与进入条件

| 阶段 | 工作与交付 | 通过条件 |
|---|---|---|
| A：前置基线 | 目标用户、一个核心问题、产品 UI 概念/高保真、API v0 契约 | 产品范围明确；关键状态可评审；接口请求、响应、错误与真实性边界明确 |
| B：官网设计 | Landing、Pricing、Waitlist 的内容、桌面/移动端高保真和表单状态 | 浏览器/截图评审；用户确认或完成明确验收；继承项目 Design-First 流程 |
| C：官网首版 | 三页、真实留资、必要声明、基础 SEO、GA4 集成 | 表单可持久保存；页面可访问；数据不虚报；生产配置就绪 |
| D：公开部署 | 正式域名、HTTPS、GSC 验证与 sitemap、生产端 GA4 验证 | 留资与分析端到端验收；GSC 能检查正式 URL；明确尚未收录的页面 |
| E：上线后优化 | 技术 SEO 复查、搜索意图与页面映射、首批内容、GEO 检查与实验记录 | 有可复查的检查结果、真实发布内容、下一轮数据观察节点 |
| F：验证与迭代 | 首周复盘；需求信号足够时启动 72 小时最小交付 | 交付一个可用结果；按实际使用决定继续、调整或暂停 |

阶段 D 的验收不以 Google 已经收录为必要条件；要证明已正确接入、可访问且已提交。收录属于后续持续观察结果。

## 3. 阶段 A/B：开发前冻结什么

### 3.1 一页产品简报

- 谁在什么场景遇到什么问题；当前怎样解决；产品准备提供什么明确结果。
- 首轮只选择一个市场和主要语言，文案、关键词、币种与获客渠道保持一致。
- 当前可以使用、开发中、规划中的能力分别列出；Roadmap 不承诺未经确认的日期。
- 明确第一版最小结果与不做清单，提前拆好约三天可交付的任务包。
- 明确验证假设，例如“遇到 X 的人愿意留下邮箱，并愿意试用 Y”；收费假设单独记录。

### 3.2 UI 与接口交付要求

产品 UI 基线用于解释产品价值；官网三页仍需单独做视觉和交互验收。先按项目要求使用 `guizang-ppt-skill` 的排版、网格、色彩、节奏和检查方法，再完成桌面与移动端评审，不机械采用横向幻灯片结构。

API v0 至少包含：接口用途、请求/响应示例、字段约束、认证和数据权限、错误状态、重复请求处理、Mock 与真实接口的标识、版本范围。只冻结首版契约，不提前设计完整商业系统。

官网接口另外补齐留资契约。建议 `POST /api/waitlist`，支持邮箱、可选套餐意向、来源、订阅用途确认和幂等键；明确无效输入、限流、服务失败、重复订阅的语义。正式 API 文档应能指导实现与验收，本方案不是已经完成的 API 交付。

视觉验收至少覆盖 390px 与 1440px，检查内容溢出、键盘操作、可见焦点、标签、错误提示、加载/成功状态。概念图有展示效果不等于真实页面已验收。

## 4. 阶段 C：官网首版范围

| 页面 | 必需内容 | 主行动 | 要验证的问题 |
|---|---|---|---|
| Landing Page `/` | 一句话价值、目标场景、核心演示、工作方式、能力状态、简短 Roadmap、FAQ | 加入候补名单 | 用户能否理解价值并愿意进一步尝试 |
| Pricing `/pricing` | 套餐差异、价格/币种/周期或明确的价格假设、适用人群、当前可用范围 | 按套餐加入候补名单 | 对何种价值与价格有初步兴趣 |
| Waiting List `/waitlist` | 邮箱表单、通知用途、可选场景、成功/错误/重复状态 | 提交邮箱 | 是否愿意留下可联系信息 |
| 必要说明 `/privacy` 等 | 实际收集什么、用途、服务商类别、保存期限、删除/退订方式、联系入口 | 查看说明或联系 | 是否理解留资和分析的边界 |

Landing 推荐信息顺序：**承诺的结果 → 具体场景 → 核心流程演示 → 当前能力与 Roadmap → 价格入口 → FAQ → 留资。**

首版不强制增加独立博客、复杂 CMS、多语言、完整支付、账号和后台管理系统。Roadmap 与 FAQ 可先作为页面区块；About/联系信息也可合并，避免为凑页数发布薄内容。

### Pricing 的真实性规则

- 尚未可购买时明确写“计划定价，产品尚未开放购买”，CTA 使用“按此套餐申请内测”等真实行动。
- 价格未确定时，可用明确标注的价格实验，或先收集预算区间；“价格待定”的名单不能解释为价格已验证。
- 套餐选择仅代表初步偏好，留邮箱不等于付费承诺。付费验证需后续真实购买或其他明确承诺。
- 先用一到两个能说明价值差异的方案，不为凑三列设计不存在的企业能力。
- 不使用虚构评价、客户 Logo、用户量、倒计时或库存。演示图要标“概念演示”；未上线能力不得写成已提供。

### Waiting List 必须形成真实闭环

1. 默认仅邮箱必填；场景和套餐意向可选，长问题放在成功后的可选反馈中。
2. 明确用户订阅什么；产品开放通知与额外营销用途区分。预先确定保存期限与删除/退订方式。
3. 优先选择已有、可导出的托管留资服务；需要自建时只增加薄接口与可靠持久存储，不先做 CRM。
4. 服务端校验、邮箱规范化与去重、限流/防机器人、幂等写入；具体邮箱规则在契约中固定，不擅自删除别名。
5. 仅在真实写入/服务接受后显示成功；数据库不可用时保留输入并允许重试，不能出现假成功。
6. 返回中性结果，避免向任意请求公开邮箱是否在名单中；重复提交不得重复计为新增线索。
7. 名单数据至少保存创建时间、套餐意向、页面/实验版本及受控来源字段；不保存任意完整 URL 或敏感查询参数。
8. 若使用邮件确认，分别记录“已提交、已确认、已退订”；未确认邮件不能算邮箱有效性已验证。发信服务与送达验收另列。

验收：使用测试地址提交 → 在真实存储中查到一条 → 刷新/重新打开后仍存在 → 重复提交不新增 → 服务失败可恢复 → 导出与删除可执行。只看到成功动画不算完成。

## 5. GSC 与 GA4：随官网上线接通

### 5.1 Google Search Console

- 准备正式域名和 DNS 权限。优先 Domain property，使用平台给出的 DNS 记录验证；只具备站点权限时按条件使用 URL-prefix property。参考 [Google 所有权验证说明](https://support.google.com/webmasters/answer/9008080?hl=en)。
- 正式部署后提交 sitemap，检查抓取/解析状态；逐个检查首页、Pricing、Waitlist 的 URL 可访问性与规范 URL。
- 记录“已提交、可抓取、已收录”三种不同状态；保存检查日期与结果，处理 robots、noindex、重定向及 canonical 错误。
- 建立搜索表现基线：展示、点击、查询、页面、国家/设备；品牌词与非品牌词分开看。

Google 明确说明，请求索引不保证收录，处理可能需要一到两周或更长。不能把 `site:` 查询作为唯一验收依据，也不能用等待一周直接证伪需求。参考 [URL Inspection 官方说明](https://support.google.com/webmasters/answer/9012289?hl=en)。

### 5.2 Google Analytics 4

建立正式站点 Web stream，部署一个 Google tag 入口，避免代码和 GTM 双重安装。开发/预览环境与生产数据分离；记录账号、属性、Measurement ID 与访问权限，不把管理员密钥放前端。

建议首版采用以下事件；除 Google 已定义的事件外，其余均为本方案自定义名称。

| 事件 | 触发条件 | 参数示例 | 判定用途 |
|---|---|---|---|
| `page_view` | 页面访问/有效路由切换，每次仅一次 | 页面路径、标题 | 基础访问 |
| `cta_click` | 点击主要 CTA | `placement`、`cta_id`、`page_version` | 哪个入口吸引用户 |
| `pricing_interest` | 选择计划套餐 | `plan_id`、`pricing_version` | 初步价格/套餐兴趣 |
| `waitlist_start` | 首次开始填写表单 | `form_id`、`placement` | 填写意愿 |
| `generate_lead` | 服务端成功接受本次新增线索后，单一上报端发送一次 | `form_id`、`plan_id`、`page_version` | 设为核心关键事件 |
| `waitlist_error` | 明确提交失败 | 受控 `error_code` | 发现技术损失 |

`generate_lead` 是 Google 推荐的线索事件；没有可靠估值时不编造收入或线索金额。参考 [GA4 推荐事件](https://developers.google.com/analytics/devguides/collection/ga4/reference/events)。

以数据库/留资服务为新增名单数量的事实来源；GA4 用于有观测覆盖的行为分析。先明确幂等和上报策略：客户端与服务端不要各报一次；重复订阅、按钮点击和失败提交不算新增线索。

普通 GA4 事件、URL、页面标题与自定义维度不传邮箱、私人材料或自由文本。来源参数采用白名单并清洗；本阶段不启用广告用户数据匹配。参考 [Google 的 PII 处理要求](https://support.google.com/analytics/answer/6366371?hl=en)。

采用保守实现：分析许可与表单订阅用途分别处理，拒绝分析仍可正常提交；跟踪失败不能阻断留资。上线前根据目标地区与实际服务配置完成相应告知及同意设计，不将一个勾选框视为全部工作完成。

验收：生产域名进行一次完整路径测试，在 [DebugView/Realtime](https://developers.google.com/analytics/devguides/collection/ga4/events) 检查事件及参数；成功事件只有一次；失败、重复、拒绝分析和禁用脚本情形符合约定。测试流量排除或明确标注。

### 5.3 首周只维护一张数据表

记录：日期、页面版本、渠道、有效观察样本、GSC 展示/点击、GA4 访问与漏斗、去重新增名单、已确认邮箱数（如采用）、明确试用意向、反馈和下一步。

- GA4 留资转化率＝同一时间窗/渠道内发生 `generate_lead` 的可观测用户 ÷ 对应落地页可观测用户；同时展示分子和分母。
- 后端新增名单数单列，不直接除以受同意或广告拦截影响的 GA4 用户数，再宣称是精确的全站转化率。
- 不将 GSC 点击和 GA4 会话当成相同口径；记录工具时区与数据更新延迟。
- 内部访问、机器人、重复线索单独处理；缺失来源记为未知，不强行归因为 SEO 或 GEO。

## 6. SEO：上线必备与上线后优化

### 6.1 上线必备基础

- 正式 URL 稳定、HTTPS 正常、公开页面返回正确状态；关键价值、价格说明与链接存在于可读取 HTML 中。
- 每页独立 title、description、明确主标题；合理的 canonical；分享标题/图片正确；图片有必要的说明。
- sitemap 只列希望收录的规范公开页面；robots 不误拦公开内容。
- 预览域名与私人产品内容限制访问/索引。`noindex` 与 robots 都不能替代真实访问控制；不要用 robots 阻止抓取后又期待爬虫读到页面上的 noindex。
- 首页、Pricing、Waitlist 可通过真实链接互达。重复和参数 URL 处理一致，不收录邮箱确认 token 或私人页面。
- 完成移动端、键盘、图片体积与基础性能检查；第三方资源尽量本地化并固定版本，不使用 `latest` CDN。
- 结构化数据仅描述页面真实可见且符合类型要求的事实，不添加假评分、未生效优惠或尚不存在的产品能力。

### 6.2 上线后第一轮优化

1. **技术复查：** 用 GSC 与实际抓取检查索引障碍、canonical、站内链接和移动端体验，先修影响访问的问题。
2. **搜索意图研究：** 围绕一个受众收集问题、替代方案与购买判断类查询；查看真实搜索结果，记录意图、竞争页面与拟提供的独特价值，不臆造搜索量。
3. **页面映射：** 同一意图集中到一页；问题/使用方式进入场景页，价格进入 Pricing，能力状态与限制进入 FAQ。优先优化现有内容。
4. **小量内容发布：** 先做一到两篇有真实示例的场景/操作内容；确有需要再做有证据的替代方案比较页。不要批量生成关键词近似的空页面。
5. **数据驱动修改：** 展示少先看收录、意图与触达；展示有而点击少检查标题与结果匹配；点击有而留资少检查价值、价格与表单。

每轮只选择一个主要变化，记录修改日期、假设与观察期。初期样本小，优先顺序实验，不把随机波动当成 A/B 测试结论。

## 7. GEO：上线后与 SEO 共用内容和证据

GEO 的目标是让生成式搜索能够准确发现、解释并引用产品，同时观察是否带来有效访问。Google 官方说明 SEO 基础仍然适用；对 Google 而言，不需要专用 AI schema 或 `llms.txt` 才能获得展示。参考 [Google 生成式搜索优化指南](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)。

### 7.1 执行动作

- **可访问：** 核心说明无需登录即可读；检查 robots、CDN/WAF 与爬虫策略，公开官网和私人产品内容分别处理。
- **事实一致：** 首页、Pricing、Roadmap 使用一致的产品名称、对象、价格口径、能力状态和联系信息。
- **真实解释：** 回答“是什么、适合谁、如何使用、有哪些限制、与现有做法有何差别”；演示给出输入和输出，按阅读需要组织，不为 AI 强行切碎内容。
- **证据可查：** 原始示例、真实体验、更新日期和引用出处可追溯；规划写成规划，效果未验证就如实说明。
- **外部发现：** 后续可在相关社区/目录发布实际有用的案例，让目标用户发现；不采购虚假提及或批量灌水。此方案本身不执行发布或联系他人。

### 7.2 按平台检查，不把训练许可当作搜索许可

| 平台 | 检查 | 证据来源 |
|---|---|---|
| Google 生成式搜索 | 除可索引和摘要资格外，核对 GSC 的 Search generative AI 设置是否包含本站，注意父级继承 | [Google 控制说明](https://support.google.com/webmasters/answer/16908024) |
| ChatGPT Search | 若希望公开官网被搜索发现，检查 `OAI-SearchBot` 的访问及防火墙；`GPTBot` 训练许可单独决策 | [OpenAI 爬虫说明](https://developers.openai.com/api/docs/bots) |
| 其他目标平台 | 按该平台当时的官方要求检查，不直接复制上述平台的许可结论 | 实施时补充对应官方链接 |

Google 的 [Generative AI performance report](https://support.google.com/webmasters/answer/16984139?hl=en) 可用于观察相关展示；报告暂不可见可能与访问开放或展示不足有关。以当前账号实际可见内容为准，不假设具有独立点击或转化维度。

### 7.3 GEO 的验收与观察

配置验收看内容能否读取、事实是否一致、访问策略是否符合选择；效果观察另外记录：

- 可获得的 Google 生成式搜索展示与落地页情况。
- GA4 中可识别的 AI 来源访问与留资；referrer 缺失时保持未知。
- 固定一小组非品牌真实问题，记录平台、日期、问题、是否引用本站以及引用是否准确；人工测试只是抽样，不代表整体覆盖率，也不据此保证排名。

“完成第一轮 GEO 优化”表示检查、内容和观察机制已交付，不表示 AI 必须推荐本站。`llms.txt` 不作为首版阻塞项；有明确使用方及收益假设时再评估。

## 8. 首轮节奏与继续开发条件

以下是以基线已通过、账号与域名可用为前提的建议时间盒，不是承诺工期。D0 指正式官网通过部署验收的当天。

| 时间 | 优先事项 | 输出 |
|---|---|---|
| 上线前约 2–4 个工作日 | 官网设计验收、三页、真实留资、基础 SEO、分析配置 | 可验收官网版本 |
| D0 | 部署、GSC、GA4、真实留资闭环检查 | 上线验收记录与数据基线 |
| D1–D3 | 技术 SEO/GEO 复查、首批高意图内容、准备并经授权执行目标渠道触达 | 页面与渠道实验记录 |
| D4–D7 | 观察漏斗；收集真实场景、替代方案、试用意向 | 第一轮诊断与一个下一步 |
| D7 之后 | 按证据继续、调整或延长观察；必要时安排 D14/D28 复盘 | 有截止节点的实验，不无限装修 |
| 达到需求信号后 72 小时内 | 削减范围，完成一个真实核心结果并向首批用户交付 | 可试用产品与实际使用证据 |

核心开发可做必要的技术可行性验证，但不应阻塞官网上线。等待数据期间可修复已有原型、验证最高风险依赖，不提前扩建完整支付、AI 或多端体系。

### 8.1 如何解读第一周

| 观察到的情况 | 目前可作的判断 | 下一步 |
|---|---|---|
| 埋点或提交链路不通 | 数据不可用 | 修复后重新建立观察窗口 |
| 未收录/几乎无目标访问 | 尚未有效触达受众 | 排查索引与渠道；增加一轮明确的目标触达，延长观察 |
| 有展示、点击少 | 可能是意图/标题/排名问题 | 查看查询与页面是否匹配，不先加功能 |
| 有目标访问、留资少 | 可能是价值不清、价格/信任/表单阻力 | 检查漏斗并了解具体原因，一次改一个主要变量 |
| 有留资、无明确使用场景 | 存在好奇心，需求证据弱 | 收集实际问题、当前解决方法与试用承诺 |
| 多名目标用户有同一痛点并愿意近期试用 | 值得推进一次小规模交付 | 启动三天任务包，验证真实使用 |
| MVP 被使用且有人愿意购买 | 商业信号增强 | 才按必要性接支付、付费权益与支持流程 |

建议事先写下本轮决策门槛。可用“至少 3 名相互独立的目标用户描述相同的具体问题，其中至少 2 名愿意近期试用”作为启动小规模 MVP 的示例工作阈值；这不是行业标准、统计显著性或产品市场匹配证明。B2B/B2C 与个人自用应重新选择阈值。

收费假设还要核对用户是否看过明确的价格与权益，并表现出相应意愿；免费名单规模不能替代付费证据。新站没有足够样本时写“尚无结论”，不要自动写“需求不存在”。

72 小时交付只包含一个入口、一个核心动作、一个真实结果及必要的数据保存。若正式技术实现无法在这个时间盒完成，可明确提供人工辅助试用，并说明实际交付方式；不把复杂未完成系统包装成成品。
