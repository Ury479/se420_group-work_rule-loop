# Agent 叠加前的真实链路核验

日期：2026-10-31。目的：在原页面设计待评审期间，验证可独立核对的接入前提。本文不改变产品方向，不代替用户界面确认，也不声明 Hermes 已运行。

## 1. 卡片关联错误已经在隔离数据库复现

当前事件详情使用 `getCards("event_case", c.id)` 和 `contextType="event_case"`。现有 `0001_account_integrity.sql` 的 `check_unified_cards_context_id` 触发器只映射 `boundary`、`event`、`task`；`check_owned_reference()` 对不支持的非空关联直接抛出 `23503`。

使用实际迁移中的函数和触发器，在新建、自动清理的 PostgreSQL 17.9 临时簇中，以单用户模式完成 6 项核对：

| 输入 | 实际结果 |
|---|---|
| 当前页面的 `event_case` + 本账号事件 | 拒绝：`23503 / Unsupported internal reference` |
| `event` + 本账号事件 | 接受 |
| `event` + 其他账号事件 | 拒绝 |
| `event` + 不存在的事件 | 拒绝 |
| 既有 `boundary` + 本账号边界 | 接受 |
| 既有 `task` + 本账号任务 | 接受 |

这是实际数据库函数行为，不是字符串匹配测试；测试仅复制必要关联结构，没有声称完成全应用 RLS 或线上验收。没有连接／重启原数据库，没有加载 `.env`，没有写入线上事件。

[结果](reference-probe.json) · [原始输出](reference-probe.log) · [复现脚本](probe-reference.py) · [两处替换的待采用补丁](event-card-context.proposed.patch)

补丁只把这两个上下文值统一为既有 `event`，未应用到生产源码。后续应用前应核对源文件哈希、当前迁移状态和是否存在历史 `event_case` 卡片；如果存在历史数据，先做账户范围的数据核对和兼容迁移，不能只改页面后让旧卡片不可见。不能用本次隔离复现推断线上已经发生了多少次保存失败。

## 2. 规则召回不等于经验适用

对当前纯函数 `selectMatchingRules()` 执行了 3 个合成案例：

- 同属 `study`：即使摘要是“提前两周准备新课程阅读”，仍召回条件为“截止前24小时仍未提交”的规则。
- 规则已暂停：排除，不能由 Agent 为了找到答案而重新加入可生效规则。
- 领域、关键词都不相关：不召回，允许没有匹配经验。

[可执行探针](probe-rule-recall.cjs) · [结果](rule-recall-probe.json)

这并非证明领域召回策略本身必须删除。它适合获取候选，但不足以证明当前满足条件。Agent 增量应按“召回 → 核对来源和状态 → 检查适用条件／排除条件 → 给出建议”处理；条件缺失、冲突或不能判断时，保持待核对，不自动计作命中有效经验。

## 3. 现有上下文出口还不足以承担经验溯源

`getEventCase()` 当前返回的 `rules` 来自 `eventCandidateRules`。复盘新建或关联的主规则保存在 `confirmationRules`，通过 `eventReviews.linkedRuleId` 关联。`generateGptContext()` 用案例数据生成文本，但没有把主规则当前版本、对应验证和带类型的稳定来源引用一起提供。

因此首版可以复用现有查询和文本导出，但不能直接把这个文本称为“完整个人经验上下文”。建议在新增 Agent 上下文解析器中补齐下列读取，保留原方法的返回形状供旧页面继续使用：

| 读取对象 | 需要带出的依据 |
|---|---|
| 当前事件与复盘 | 归属、原始字段、事件关联；自述与 AI 假设分开 |
| 案例候选规则 | `event_candidate_rule` 类型、来源案例、候选状态；不冒充主规则 |
| 复盘关联的主规则 | `confirmation_rule` 类型、`currentVersion`、状态、来源对象、触发条件 |
| 主规则版本与验证 | 使用哪一版、实际结果、帮助程度及反例；未验证就如实标记 |
| 相似历史事件 | 候选筛选理由、原事件／复盘入口及差异；不能只提供一个标题 |

两个规则表都有 ID 和状态，但命名及生命周期不同。类型和 ID 必须一起解释，不得按裸数字 ID 混合，也不能把两表的 `active` 状态都解释成“已经验证有效”。

来源快照应有可定位的字段及原文、稳定的类型／ID 引用、读取时状态、版本或内容哈希。`eventReviews` 没有 `updatedAt`，不能在所有来源上虚构“最后更新时间”版本校验；应按选定原始字段做规范化内容哈希，并在采纳前重新读取比较。语言呈现不改变源字段、ID 或证据性质。

建议的适用性输出是“有依据／不适用／信息不足”，附引用及理由。模型不能自行创建可信来源；服务端只接受本次已授权来源集合内、仍可读取且版本一致的引用。

## 4. Hermes 协议的核验范围

本轮重新读取了 [官方 API Server 文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server)，确认可通过能力发现和 runs 提交／状态接口接入，不需要为了 RuleLoop 重新设计一套 Hermes REST 协议。文档随上游演进，不能代替所选运行版本的实测。

同时读取此前保存的固定提交 `78077b2b8f83ac7d9293d3269df7ef20e3a9a994` 的 3 个源码文件，重算 Git blob SHA，与此前记录的固定文件标识一致。官方提交页可访问；本轮未重新下载全部固定版本源码，不声称已重建完整发行包。

从该源码 AST 中仅提取并执行纯函数 `terminal_run_status()`，核对 7 类结果：完成、部分输出、明确失败、明确未完成、迭代预算耗尽、带文字的中断，以及缺少完成标记的空结果。没有 import 完整 Hermes、安装依赖或启动 gateway。

这里发现一个接入边界：该内部函数把空结果映射成 `completed`，因此 RuleLoop 不能仅因某层返回“完成”或一段文字就接受建议。还必须核对受认证的运行 ID 与终态、业务上下文、结构化输出及来源。该内部函数的行为也不意味着 Hermes HTTP 接口接受空响应，本次没有做这种推断。

[源码标识与纯函数结果](hermes-source-probe.json) · [探针](probe-hermes-source.py)

已有独立候选中的 HTTP 传输、来源校验等实现可以按这些边界筛选复用。独立应用认证、业务行动表和学习主流程不能整体移入当前架构；现有候选测试通过也不证明真实 Hermes 的工具、记忆、账号隔离及费用已验收。

## 5. 对实现顺序的具体调整

1. P0 前置：统一事件卡片上下文命名，先核对历史数据，再验证原人工卡片保存。
2. P0 上下文：从原事件和已关联主规则补齐有类型的来源、版本和结果依据；保留原文本出口。
3. P0 Agent：把既有规则匹配作为候选召回，独立判断适用性；无可靠依据时允许不推荐。
4. P0 采纳：重新校验来源与业务状态，经原 action 写入原卡片、复盘或规则对象。模型等待不持有账户数据库事务。
5. 原页面交互确认后，再选择实际 Hermes 构建与提供商／预算，进行运行能力、来源撤回、账号边界、超时和取消的真实验收。USD／CNY／THB 结算与三语要求继续保留，未因本次技术探针而完成。
