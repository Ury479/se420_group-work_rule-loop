# RuleLoop 功能盘点与首页聚焦评审

2026-11-11 · 账号版源码与本机测试账号。独立官网不在本轮范围内。用户在本轮明确选择了两个日常场景：① 遇到一笔支出，决定买不买或复盘为什么买；② 遇到具体事件，记录、复盘并找到下次做法。

## 问题陈述

- **我是谁：** 已有两个明确使用场景的 RuleLoop 个人使用者，偶尔会带着一笔支出或一件刚发生的事打开应用。
- **我想做到：** 在付款前把这笔钱想清楚，或者记下发生的事，复盘时留下一条下次能用的做法。
- **我遇到的阻碍：** 手机上点「记录」会进入布防，点「待复盘」会进入高额支出审查。回到首页也要从人生时间、任务、习惯、确认和各种指标里找到手头那条记录。
- **原因：** 账号版保留了多套工作流，菜单按已有模块命名；首页的待确认、换算和事件库待复盘各用不同的数据源，没有围绕当前事情给出可辨认的下一步。
- **实际影响：** 用户说「感觉很多功能页面用不上，但又说不清楚」。本轮没有其他用户的使用记录，也没有测量入口耗时或访问频次。

**一句话：** 当我为一笔支出或一件事件打开 RuleLoop 时，我需要直接开始判断、记录，或接回之前的复盘，因为目前多个入口名称与它们实际处理的对象不一致，我得先搞懂模块才能继续手头的事。

## 源码盘点

共 **68 个页面路由定义**：64 个原账号版定义、3 个旧路径兼容入口，加上 `/habits`。动态路由的列表、详情、编辑、检查和导出都各占一个定义，不能按 68 个独立功能解读。

| 功能组 | 路由数 | 当前实现及用途 | 建议 |
| --- | ---: | --- | --- |
| 消费换算 | 3 | `/convert` 选择比较项，保存金额与换算快照，管理目录，冷静期后回填实际决定；与档案有数据连接 | **核心**：首页一键打开；有回看时直达原记录；价值目录留在换算流程 |
| 支出审核与复盘 | 9 | `/spending-review` 有独立审查记录、风险分层、冷静期/人工决定、事后复盘、协议、消费参照物、恢复动作；Markdown 与 GPT 结果是复制/下载、外部审核、手动回填的路径 | **核心场景内的深度工具**：首页保留一个明确入口；不要让它冒充所有事件的待复盘 |
| 事件与通用复盘 | 8 | `/event-library` 有新增、详情、搜索、模式、规则、统计；`/reviews/new` 随事件 ID 或确认 ID 走不同表单；普通事件支持只保存或保存并复盘 | **核心**：首页一键记事件，待复盘直达原事件的复盘任务；搜索、统计、模式留在事件库 |
| 提前布防与关键确认 | 6 | `/arm`、`/quick-check` 和 `/critical-confirmations/*` 会记录风险、建检查项并保存完成证据；处理的是事前检查 | **按需**：单独命名「提前布防」「快速检查」；不占普通「记录」入口 |
| 规则与成长档案 | 4 | `/rules` 有详情、启停及验证；事件库另有候选规则；`/archive` 汇总事件、复盘、规则和换算等真实记录 | **次入口**：保留查询和证据回看；把状态、来源和规则种类说清楚 |
| 任务与习惯 | 2 | `/tasks` 有任务树、优先级、截止与进度；`/habits` 有账号打卡、最多两项启用、暂存及热力图 | **更多**：保留任务和「习惯打卡」入口；首页不默认展开任务或使用含义不明的「继续上次」 |
| 作息、时间与状态 | 6 | `/morning-routine`、`/night-ritual` 保存作息，`/lifespan` 汇总生命周、近期任务等，`/mind-regulation` 有状态与行动，`/entertainment` 有记录与评估 | **更多**：保留各自工作区；寿命估算退出首页首屏 |
| 人际与资源 | 14 | `/relationships/*` 有关系筛查、互动、边界与复盘；`/resources/*` 管理资源、人和配置方案 | **更多**：按场景放在一起；下级功能由所属工作区进入 |
| 边界、需求、弱点与备忘 | 8 | `/boundaries/*` 有执行检查；`/demands` 有需求列表和状态；`/weakness` 可检测、记录和更新弱点；`/ash-memos/*` 可整理教训并关联规则 | **更多**：有实际数据和后续操作，按需使用 |
| 首页、账户、独立翻译 | 5 | 首页与设置、登录/注册；`/translate` 是单独的文本翻译功能，线上模型接入未在本轮核验 | **保留**：账户与翻译归类在更多；界面中英切换仍是独立能力 |
| 旧地址兼容 | 3 | `/record`、`/review`、`/review/[id]` | **保留**：历史地址跳转 |

## 优先处理的证据

1. **手机入口说的和做的不同。** [导航配置](../../../src/components/app-nav.tsx) 的「记录」跳到 `/arm`（80% 布防），「待复盘」跳到 `/spending-review`（高额支出审查）。[普通事件](../../../src/app/event-library/page.tsx) 有真实待复盘状态，但手机主导航不直接通向事件库。这是入口错位，背后的功能可以复用。
2. **首页的「待复盘」和最近轨迹缺少可信状态。** [首页](../../../src/app/page.tsx) 里的「待复盘」计数取自待确认的 `pending/armed/checking`，与事件库未复盘数量无关；最近轨迹按第 1、2、3 行分别贴「复盘中／已关联规则／已存档」，与该条记录状态无关；闭环的「已记录」写死为完成。测试账号的首页确实把「提交课程报告」显示为「复盘中」。建议用可点开的真实记录替换这些组件。
3. **两套消费流程各有记录。** [换算回看](../../../src/app/actions/spend-conversion.ts) 选一条未结算的冷静期记录；[支出审核台](../../../src/app/spending-review/page.tsx) 另有冷静期、待外部 GPT 审核和人工决定队列。首页统一表达为消费场景，先通过入口与返回路径连接；无需在这一轮合并两张业务表。当前换算回看优先仍在计时的条目；若做可行动队列，需要单独查询已结束未记录的条目，避免它们被仍在计时的条目挡住。
4. **两个规则入口代表不同生命周期。** [事件复盘提交](../../../src/app/actions/event-library.ts) 可以同时创建事件候选规则和拦截规则草稿；[复盘表单](../../../src/components/mini-review-form.tsx) 可以把同一句最小行动传给两者。用户看到两个「规则」很难知道下次该用哪条。第一步区分「事件候选规则」和「可复用的规则」，等真实案例证明重复维护造成损耗，再决定是否合并写入。
5. **有一个可确定的断链。** 支出详情「查看完整协议」原来指向不存在的 `/decision-baseline`。在本机测试账号中点击到 404。已把链接指回应用现有的 `/spending-review/baseline`。

## 原型方案和生产验收

原型只演示入口、顺序和状态。用同一石白配色和单一强调色，桌面将「开始一件事」「可以继续」并排，手机按相同阅读顺序排列。每个首要入口包含动词和对象，使用紧凑的分隔线区分动作。卡片下面只有「支出审查与复盘」一个深度入口。可切换有待处理、冷静期中和空态，原型记录都是样例；正式版本的链接直达已有页面。当前方案把首页的内嵌金额输入收进现有换算页，首页少一块表单，直接在首页填金额的用户会多点一次。

- 首屏可分别打开消费换算和普通事件记录；已有支出审核可从显式入口继续。移动端能直接打开事件库，不再把「待复盘」连到只含支出的队列。
- 待办直接回到原记录：冷静期结束进入该笔换算填结果；普通事件进入该事件的复盘；支出审核待人工确认则打开原审核。仍在冷静期的项目标出结束时间，不计入待处理数。待关键确认放在「更多 → 决策与经验」里继续处理。需要先区分「可处理」「等待时间」「已经完成」。
- 没有记录时，两条开始路径照常显示，待办区域明确空态，不展示推测的进度或指标。
- 规则、档案从首页「回看」进入；任务、习惯、寿命、作息等通过「更多」抵达。沿用已有数据和 URL，已保存的桌面导航顺序可用于更多内排序，具体兼容方式待生产开发确认。
- 生产验收在 390px 手机和 1440px 桌面用隔离账号验证；覆盖键盘、焦点、刷新、空态、待办来源、直达 URL、旧链接与中英切换。涉及首页换算时跑现有 `localizes the spending comparison` 端到端回归。随后用两条实际使用场景验证：进入原记录之前是否还需要先想它属于哪个模块。

已用 Chromium 在 390px、768px、1440px 核对离线原型：首屏动作和待处理条目不被底栏挡住，点击跳到预期工作区，键盘可激活，切页后焦点移到标题，冷静期和空态显示正确，无横向溢出或外部请求。另在本机 `ruleloop_test` 运行生产构建：协议链接可从详情点开，刷新返回 200；事件到复盘、规则与档案，消费换算中英切换，以及支出审核与导出三条现有端到端测试通过。

首页及主导航目前是离线原型。应用源码中只修正了已确认的断链，未部署。
